# 004. Post 수집 - 주기, 실패 처리, 저장 범위

## 0. 문서 정보

- Status: Accepted
- Date: 2026-08-30
- 관련 Spec: `docs/specs/feed.md`
- 관련 Decision: `003-blog-discovery.md`, `009-ephemeral-state.md`

---

## 1. Context

`docs/specs/feed.md`는 수집 동작을 정의하고 구체적인 수치는 이 Decision으로 넘겼다. 정할 것:

- 수집 주기
- 첫 수집 시 저장할 Post 개수
- `FAILING` → `UNAVAILABLE` 전환 임계값과 재시도 간격
- 외부 플랫폼 동시 요청 제한
- 저장 범위 (본문, 발췌, 썸네일)

제약: 외부 블로그 플랫폼은 우리 서비스를 위해 존재하지 않는다. 우리가 보내는 요청 총량을 우리가 통제해야 한다.

---

## 2. Decision

### 수집 주기

| 항목 | 값 |
| --- | --- |
| 기본 주기 | 30분 |
| 스케줄러 실행 간격 | 5분 (그 시점에 주기가 된 Blog만 처리) |
| Subscription 최초 생성 시 | 즉시 1회 |

- 스케줄러는 5분마다 돌지만, 각 Blog는 마지막 시도 후 30분이 지났을 때만 대상이 된다.
  전체 Blog를 한 번에 치지 않고 시간에 분산시키려는 구조다.
- 한 번의 스케줄러 실행에서 처리할 Blog 수에 상한을 둔다. 초기값 100.

### 첫 수집 범위

| 항목 | 값 |
| --- | --- |
| 첫 수집 저장 개수 | 최신 20건 |
| 이후 수집 | Feed에 있는 항목 전체를 확인하되 새 것만 저장 |

첫 수집으로 저장된 Post는 `isNew: false`다. (`feed.md` FR-003)

### 실패 처리

| 항목 | 값 |
| --- | --- |
| `ACTIVE` → `FAILING` | 연속 실패 1회부터 |
| `FAILING` → `UNAVAILABLE` | 연속 실패 10회 |
| 영구 실패(404, 410) | 즉시 `UNAVAILABLE` |
| 재시도 간격 | 30분 × 2^(연속실패-1), 최대 24시간 |
| `UNAVAILABLE` 재시도 | 24시간마다 |

재시도 간격 예: 1회 실패 후 30분, 2회 후 1시간, 3회 후 2시간, ... 6회 후 16시간, 이후 24시간 고정.

- `UNAVAILABLE`도 완전히 포기하지 않는다. 블로그가 일시적으로 내려갔다 돌아올 수 있다.
- 한 번이라도 성공하면 `ACTIVE`로 복귀하고 연속 실패 카운터를 0으로 만든다.
- `FAILING` 이상이면 사용자에게 마지막 정상 수집 시각을 보여준다. (`feed.md` FR-011)

### 동시 요청 제한

| 항목 | 값 |
| --- | --- |
| 전체 동시 수집 | 5 |
| 같은 호스트 동시 요청 | 1 |
| 같은 호스트 최소 요청 간격 | 1초 |

- 같은 호스트에 동시 요청 1은 강한 제약이지만, Naver Blog나 Velog처럼 사용자가 몰릴 호스트를 우리가 두드리는 상황을 막는다.
- 호스트 판단은 Feed 주소의 호스트 기준이다.
- 스케줄러 스레드 풀 크기로 전체 동시 수집을 제한한다. (`009-ephemeral-state.md`)

### 외부 요청 상한

`003-blog-discovery.md`의 값을 그대로 쓴다. 연결 3초, 응답 5초, 본문 2MB, 리다이렉트 3회.

### 저장 범위

**본문을 저장하지 않는다. 발췌도 저장하지 않는다.**

| 항목 | 저장 | 비고 |
| --- | --- | --- |
| 제목 | O | 없으면 해당 항목을 건너뛴다 |
| 원문 URL | O | |
| 게시 시각 | O | 없거나 미래면 수집 시각으로 대체하고 `publishedAtEstimated: true` |
| 썸네일 URL | O | 원본 주소를 그대로 참조. 재호스팅하지 않는다 |
| 발췌(excerpt) | X | |
| 본문 | X | |

발췌를 저장하지 않는 이유:

- 글 확인은 원본 플랫폼에서 한다는 방향이 정해졌다. 피드는 "누가 뭘 썼는지" 알려주는 역할이다.
- 발췌를 저장하면 저장 범위가 어디까지인지가 계속 논쟁거리가 된다. 안 하는 쪽이 P-006에 명확히 맞는다.
- Feed 항목의 `description`은 플랫폼마다 전문/요약/빈값이 섞여 있어 일관된 발췌를 만들 수 없다.

썸네일은 원본 URL을 그대로 참조한다.

- 저장하지 않으므로 이미지 저작권과 저장 비용 문제가 없다.
- 원본이 사라지면 이미지가 깨진다. 클라이언트는 썸네일 로드 실패를 정상 상태로 처리한다.
- 썸네일 추출 순서: `media:thumbnail` → `enclosure`(image 타입) → `og:image`는 시도하지 않음(추가 요청이 필요하므로).
  못 찾으면 `null`이고, 화면은 썸네일 없는 레이아웃으로 렌더한다.

### 보관

- Post를 자동 삭제하지 않는다. MVP 규모에서 정리 작업이 필요 없다.
- 모든 구독이 해제된 Blog는 수집 대상에서 빠지지만 Post는 남는다. (`feed.md` FR-001)

## 3. Alternatives

| 대안 | 장점 | 단점 | 선택하지 않은 이유 |
| --- | --- | --- | --- |
| 수집 주기 5~10분 | 새 글을 빨리 발견 | 외부 요청량이 3~6배. 블로그는 그렇게 자주 올라오지 않는다 | 얻는 것보다 부담이 크다 |
| 수집 주기 6시간 | 요청량 최소 | "새 글을 놓치지 않는다"는 제품 가치가 약해진다 | 제품 목적과 어긋난다 |
| 발췌 저장 | 피드에서 내용을 미리 볼 수 있다 | P-006 경계가 흐려지고 플랫폼별 품질이 불균일 | 원본에서 읽는 방향으로 정했다 |
| 썸네일 재호스팅 | 원본 삭제에도 안전, 최적화 가능 | 저장 비용, 저작권, 이미지 파이프라인 필요 | MVP 범위를 넘는다 |
| Conditional GET (ETag/Last-Modified) | 요청 비용 절감 | 상태 저장이 늘어난다 | 이득이 있으므로 재검토 대상으로 남긴다 (6장) |

---

## 4. Trade-off

- 30분 주기이므로 새 글 발견까지 최대 30분 지연된다. 실시간 알림 제품이 아니므로 수용한다.
- 같은 호스트 동시 1 + 최소 간격 1초는, 같은 플랫폼 블로그를 많이 구독할수록 전체 수집 완료가 느려진다.
  Naver Blog 100개를 구독하면 한 바퀴에 최소 100초다. 5분 간격 스케줄러 안에서는 문제없지만 규모가 커지면 재검토한다.
- 발췌가 없으므로 피드는 제목과 날짜, 썸네일만 보여준다. 정보량이 적다는 피드백이 나올 수 있다.
  나오면 그때 P-006과 함께 다시 판단한다. 저장하지 않는 쪽이 되돌리기 쉽다.
- 지수 백오프 최대 24시간이므로, 오래 죽어 있던 블로그가 살아난 뒤 최대 24시간 늦게 감지된다.

## 5. Consequences

### `feed.md` 수정 필요

`feed.md`의 다음 내용이 이 Decision과 어긋난다. 같은 PR에서 수정한다.

- 7장 Post 데이터의 `excerpt` 항목 제거
- 8장 응답 예시의 `excerpt` 필드 제거
- FR-005의 "짧은 발췌 (있는 경우, 상한 길이로 자름)" 제거
- 11장 Open Questions의 "`excerpt` 최대 길이", "썸네일을 원본 참조로 둘지" 제거

### 구현에서 지킬 것

- 수집은 외부 호출 후 짧은 트랜잭션에서 저장한다. 외부 응답을 기다리며 커넥션을 잡지 않는다. (`007-persistence-stack.md`)
- 중복 방지는 `INSERT ... ON CONFLICT DO NOTHING`으로 DB에 맡긴다. 조회 후 판단하지 않는다. 경합에서 깨진다.
- 항목 일부가 파싱 실패해도 나머지는 저장한다. 실패 항목 수를 로그에 남긴다. (`feed.md` 9장)
- 수집 실패를 삼키지 않는다. `BlogFetchState`에 상태와 실패 종류를 남긴다.

### 테스트

- 스케줄러 테스트는 고정 sleep으로 기다리지 않는다. 수집 대상 선정 로직과 상태 전이를 순수 함수로 분리해 시간 값을 주입해 검증한다.
- 백오프 계산은 단위 테스트로 검증한다.
- 중복 수집 방지는 Testcontainers Postgres에서 검증한다. (`001-database-selection.md`)

## 6. 재검토 조건

- 사용자가 "새 글이 늦게 뜬다"고 느낄 때 (주기 단축 검토)
- 특정 플랫폼에서 429나 차단을 받을 때 (동시성과 간격 재조정)
- Conditional GET(ETag, Last-Modified) 도입으로 요청 비용을 줄일 때
- 피드 정보량 부족 피드백이 반복될 때 (발췌 저장 재검토)
- Blog 수가 늘어 한 바퀴 수집 시간이 주기를 넘길 때
