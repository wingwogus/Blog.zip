# 009. 단기 상태 저장 - 인메모리 (단일 인스턴스 전제)

## 0. 문서 정보

- Status: Accepted
- Date: 2026-08-30
- 관련 Spec: `auth.md`, `blog-subscription.md`, `feed.md`, `blog-ownership.md`
- 관련 Decision: `001-database-selection.md`, `002-auth-strategy.md`

---

## 1. Context

Spec에는 영속 엔티티가 아닌 단기 상태가 여러 개 있다.

| 상태 | 출처 | 성격 |
| --- | --- | --- |
| `lookupToken` | `blog-subscription.md` FR-003 | 분 단위 만료, 1회성 |
| 로그인 실패 횟수 | `auth.md` FR-006 | 분 단위 윈도우 카운터 |
| 탐색 요청 제한 | `blog-subscription.md` 9장 | 사용자별 rate limit |
| Ownership 확인 요청 제한 | `blog-ownership.md` FR-004 | 사용자별 rate limit |
| 수집 스케줄러 실행 조율 | `feed.md` FR-002 | 중복 실행 방지 |
| refreshToken 유효성 | `auth.md` FR-004 | 로그아웃 시 무효화 필요 |

MVP는 애플리케이션 인스턴스 1대로 운영한다.

---

## 2. Decision

**단기 상태는 인메모리에 둔다. 단, refreshToken은 예외로 PostgreSQL에 저장한다.**

### 인메모리로 두는 것

| 상태 | 구현 | 유실 시 영향 |
| --- | --- | --- |
| `lookupToken` | 만료 기반 캐시 (Caffeine) | 사용자가 URL 입력 단계를 다시 밟는다. Spec에 이미 `400 LOOKUP_EXPIRED` 처리가 있다 |
| 로그인 실패 카운터 | 만료 기반 캐시 | 재시작 시 카운터 초기화. 공격자가 재시작을 유발할 수단은 없다 |
| 요청 제한 카운터 | 만료 기반 캐시 | 재시작 시 초기화 |
| 스케줄러 조율 | `@Scheduled` + 단일 스레드 풀 | 인스턴스가 1대이므로 락이 필요 없다 |

- 만료 시간과 최대 엔트리 수를 반드시 지정한다. 상한 없는 `Map`을 쓰지 않는다. 무한 증가하면 OOM이다.
- Caffeine 하나로 위 세 가지를 모두 처리한다. 별도 캐시 라이브러리를 추가하지 않는다.

### refreshToken은 DB에 저장한다

인메모리로 두지 않는 이유:

- `auth.md` FR-004는 로그아웃 시 refreshToken 무효화를 요구하고, AC에는 "로그아웃 후 재발급 요청 시 `401`"이 있다.
- 인메모리 저장이면 **배포나 재시작마다 모든 사용자가 로그아웃된다.**
  MVP 단계에서 배포는 잦고, 매 배포마다 전원 로그아웃은 사용자가 체감하는 결함이다.
- refreshToken 검증은 요청당 최대 1회고 빈도가 낮다. DB 조회 비용이 문제되지 않는다.

저장 방식은 `002-auth-strategy.md`에서 정한다. SHA-256 해시로 PostgreSQL에 저장한다.

## 3. Alternatives

| 대안 | 장점 | 단점 | 선택하지 않은 이유 |
| --- | --- | --- | --- |
| Redis | 인스턴스 증설 시 그대로 확장, TTL 기본 제공, 재시작에 안전 | 운영 컴포넌트 하나 추가, 로컬 개발에 컨테이너 하나 더 | 단일 인스턴스에서 얻는 게 없다. 필요해지는 시점이 명확하므로 그때 넣는다 |
| 전부 PostgreSQL | 컴포넌트 추가 없음, 재시작에 안전 | 짧은 TTL 데이터로 테이블이 지저분해지고 정리 작업이 필요 | rate limit 카운터를 DB에 쓰는 건 과하다 |
| 전부 인메모리 (refreshToken 포함) | 가장 단순 | 재시작마다 전원 로그아웃 | 사용자가 체감하는 결함이다 |
| Spring Session + JDBC | 세션 관리 표준화 | 토큰 기반 인증에 세션 개념이 겹친다 | 인증 방식과 맞지 않는다 |

---

## 4. Trade-off

**이 결정은 인스턴스가 1대라는 전제에 의존한다.** 인스턴스를 2대로 늘리는 순간 다음이 깨진다.

- rate limit이 인스턴스별로 따로 세어져 실질 허용량이 인스턴스 수만큼 늘어난다.
- `lookupToken`을 발급한 인스턴스와 다른 인스턴스로 생성 요청이 가면 `400 LOOKUP_EXPIRED`가 난다.
- 수집 스케줄러가 인스턴스마다 돌아 같은 Blog를 중복 수집하고, 외부 플랫폼에 요청이 두 배로 간다.

세 번째가 가장 위험하다. 외부 블로그 플랫폼에 대한 요청 수는 우리가 통제해야 하는 값이다.

그래서 이 제약을 코드 주석이 아니라 이 문서에 남긴다. **인스턴스를 늘리는 작업에는 반드시 이 Decision 재검토가 포함된다.**

---

## 5. Consequences

- 로컬 개발에 필요한 외부 컴포넌트는 PostgreSQL 하나다.
- 배포는 재시작을 수반하므로 진행 중이던 `lookupToken`이 무효가 된다. 클라이언트는 이미 `LOOKUP_EXPIRED`를 처리한다. (`blog-subscription.md` 9장)
- 캐시 설정값(TTL, 최대 크기)은 설정 파일에 두고 코드에 하드코딩하지 않는다.
- 수집 스케줄러는 `@Scheduled`로 구현하고, 스레드 풀 크기로 외부 요청 동시성을 제한한다. (`feed.md` FR-002)
- 인스턴스 수를 늘리기 전에 최소한 스케줄러 분리 또는 분산 락이 먼저 필요하다.

---

## 6. 재검토 조건

- 인스턴스를 2대 이상으로 늘릴 때 (필수 재검토)
- 무중단 배포를 도입할 때
- 수집 스케줄러를 별도 프로세스로 분리할 때
- rate limit을 정확히 보장해야 하는 요구가 생길 때
