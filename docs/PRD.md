# 1. 제품 개요

## 한 줄 소개

**플랫폼에 상관없이 친구들의 블로그를 한곳에서 구독하고 보는 소셜 블로그 피드.**

## 제품 설명

블로그를 운영하는 사람들은 네이버 블로그, Velog, Tistory, 개인 블로그 등 서로 다른 플랫폼을 사용한다.

각 플랫폼은 자체적인 구독 또는 팔로우 기능을 제공하지만, 대부분 해당 플랫폼 내부에서만 동작한다.

Blog.zip은 사용자가 친구의 블로그 주소를 등록하면 해당 블로그의 새 글을 지속적으로 확인하고, 여러 플랫폼에 흩어진 친구들의 글을 하나의 피드에서 볼 수 있도록 한다.

사용자는 RSS나 Atom 같은 기술적인 개념을 알 필요가 없다.

일반적인 블로그 URL을 입력하고 해당 블로그가 누구의 블로그인지 지정하면 친구가 피드에 추가된다.

Blog.zip은 단순 RSS Reader보다 **사람과 관계를 중심으로 블로그를 구독하는 경험**을 목표로 한다.

---

# 2. 배경

블로그는 여전히 개인의 생각, 일상, 경험, 기술 지식, 회고 등을 기록하는 주요 수단 중 하나다.

그러나 블로그 서비스가 여러 플랫폼으로 분산되면서 사람을 지속적으로 구독하는 경험 역시 플랫폼별로 분리되어 있다.

예를 들어 사용자가 여러 친구의 블로그를 보고 싶어도 각각 사용하는 플랫폼이 다르면 다음과 같은 행동이 필요하다.

- 각 블로그 주소를 기억한다.
- 직접 블로그를 방문한다.
- 해당 플랫폼 계정을 만든다.
- 플랫폼별 구독 기능을 각각 사용한다.
- 새 글이 올라왔는지 직접 확인한다.
- 메신저 등에서 공유된 링크를 통해 글을 발견한다.

기존 RSS Reader를 사용하면 여러 블로그를 하나의 피드에서 볼 수 있지만 일반 사용자가 RSS 주소를 직접 찾거나 Feed 구조를 이해해야 하는 경우가 많으며, 서비스 경험 역시 블로그나 Feed 단위로 구성되어 있다.

Blog.zip은 이러한 문제를 **친구의 블로그를 추가한다**는 친숙한 경험으로 해결한다.

# 3. 문제 정의

## 핵심 문제

사용자가 읽고 싶은 사람들의 블로그가 서로 다른 플랫폼에 존재할 경우 해당 사람들의 새로운 글을 하나의 공간에서 지속적으로 확인하기 어렵다.

## 세부 문제

### 플랫폼별 관계 분리

각 블로그 플랫폼의 구독 관계가 해당 서비스 내부에 종속되어 있다.

### 반복적인 확인 비용

친구가 글을 작성했는지 확인하려면 여러 사이트를 직접 방문해야 한다.

### RSS의 높은 진입장벽

RSS를 이용하면 문제를 해결할 수 있지만 일반 사용자가 RSS 주소와 구독 개념을 직접 다뤄야 한다.

### 친구가 서비스에 가입해야 하는 소셜 서비스의 한계

일반적인 소셜 서비스는 상대방도 서비스에 가입해야 관계가 형성된다.

그러나 Blog.zip에서 보고 싶은 친구는 Blog.zip을 사용하지 않을 수도 있다.

### 글쓰기 활동의 분산

친구들과 블로그 포스팅 챌린지를 진행할 경우 작성 여부나 글 링크를 메신저 등 별도의 공간에서 관리해야 한다.

---

# 4. 제품 목표

Blog.zip의 목표는 다음과 같다.

- 여러 플랫폼의 친구 블로그를 하나의 피드에서 확인할 수 있도록 한다.
- 블로그 플랫폼보다 사람을 중심으로 구독하도록 한다.
- 친구가 Blog.zip에 가입하지 않아도 해당 블로그를 구독할 수 있도록 한다.
- RSS와 같은 기술적 개념을 사용자 경험에서 최대한 숨긴다.
- 사용자가 블로그 URL만으로 쉽게 친구를 추가할 수 있도록 한다.
- 본인의 블로그를 Blog.zip 계정과 연결할 수 있도록 한다.
- 구독과 블로그 소유권을 명확히 분리한다.
- 장기적으로 친구들과 함께 글을 쓰고 지속할 수 있는 소셜 경험을 제공한다.

---

# 5. Non-Goals

Blog.zip은 초기 단계에서 다음 목적을 가지지 않는다.

- 새로운 블로그 작성 플랫폼 제공
- 블로그 호스팅
- 전문 RSS Reader 제공
- 검색 엔진 제공
- 전체 인터넷 콘텐츠 추천 플랫폼 구축
- 원본 플랫폼의 댓글 시스템 대체
- 원본 플랫폼의 좋아요 및 공감 기능 통합
- SNS 수준의 공개 프로필 및 팔로워 경쟁 구조 구축
- AI 기반 콘텐츠 생성 서비스 제공

Blog.zip은 **친구들의 외부 블로그 콘텐츠를 발견하고 지속적으로 읽는 경험**에 집중한다.

# 6. 타깃 사용자

## Primary User

서로 다른 플랫폼에서 블로그를 운영하거나 친구들의 블로그를 지속적으로 읽는 사용자.

주요 사용 상황은 다음과 같다.

- 친구들이 서로 다른 블로그 플랫폼을 사용한다.
- 친구의 새로운 글을 놓치지 않고 읽고 싶다.
- 자주 읽는 개인 블로그를 한곳에서 관리하고 싶다.
- 친구들과 블로그 글쓰기 활동을 함께하고 싶다.

## Secondary User

개인적으로 관심 있는 사람들의 블로그를 지속적으로 읽고 싶은 사용자.

반드시 실제 지인 관계일 필요는 없으며 특정 개인의 블로그를 지속적으로 구독하려는 사용자도 포함한다.

---

# 7. 핵심 제품 원칙

## P-001. People First

기술적인 데이터 구조에서는 Blog 또는 Feed를 구독하지만 사용자 경험에서는 **사람을 추가하고 사람의 글을 보는 것**처럼 느껴져야 한다.

블로그 URL보다 해당 블로그를 운영하는 사람이 중심이 된다.

---

## P-002. RSS Abstraction

RSS, Atom 등의 기술적 개념을 기본 사용자 경험에서 노출하지 않는다.

사용자는 일반 블로그 URL을 입력하고 Blog.zip이 가능한 경우 Feed를 자동으로 탐색한다.

---

## P-003. Subscription과 Ownership 분리

공개 블로그를 구독하는 행위와 해당 블로그의 실제 소유자임을 주장하는 행위는 다른 개념이다.

블로그를 구독하는 데에는 소유권 인증이 필요하지 않다.

본인의 블로그로 계정에 연결하는 경우에만 소유권 인증이 필요하다.

---

## P-004. 비가입 사용자 구독 가능

블로그 운영자가 Blog.zip에 가입하지 않았더라도 해당 블로그를 구독할 수 있어야 한다.

Blog.zip의 가치는 친구들의 가입 여부에 의존하지 않아야 한다.

---

## P-005. 낮은 초기 진입장벽

사용자가 한 명만 가입한 상태에서도 즉시 서비스를 사용할 수 있어야 한다.

친구 전체를 초대하거나 가입시키는 과정이 선행되어서는 안 된다.

---

## P-006. Original Content First

원본 콘텐츠의 출처와 원문을 존중한다.

Blog.zip은 콘텐츠를 새롭게 작성하거나 원본 플랫폼을 대체하지 않는다.

피드는 콘텐츠 발견과 구독 경험에 집중하며 사용자는 필요할 경우 원문으로 이동한다.

---

## P-007. 관계는 사용자 기준으로 해석

구독자가 특정 블로그에 지정한 사람 이름은 해당 사용자의 개인적인 Label이다.

같은 블로그를 여러 사용자가 서로 다른 이름으로 저장할 수 있다.

사용자가 입력한 이름만으로 특정 Blog의 실제 소유자를 결정하지 않는다.

---

# 8. 핵심 개념

## User

Blog.zip에 가입한 사용자.

사용자는 블로그를 구독하거나 자신의 블로그를 연결할 수 있다.

---

## Blog

Blog.zip이 콘텐츠를 수집하는 외부 블로그.

지원 대상에는 다음과 같은 유형이 포함될 수 있다.

- Naver Blog
- Velog
- Tistory
- 개인 블로그
- 기타 RSS 또는 Atom 지원 블로그

지원 플랫폼 범위는 Feature Spec에서 관리한다.

---

## Subscription

User가 특정 Blog의 글을 자신의 피드에서 보기 위해 생성한 관계.

Subscription에는 구독자가 해당 블로그에 지정한 이름 등의 개인 설정을 저장할 수 있다.

Subscription은 Blog의 소유권을 의미하지 않는다.

---

## Ownership

특정 User가 특정 Blog의 실제 운영자라는 것을 인증한 관계.

Ownership 생성에는 별도의 소유권 확인 절차가 필요하다.

---

## Post

외부 Blog에서 발견한 게시물.

Post는 Blog에 속하며 Blog.zip Feed를 구성하는 기본 콘텐츠 단위다.

---

## Challenge

사용자들이 일정 기간 동안 포스팅 목표를 공유하고 진행 상황을 확인하는 기능.

Challenge는 제품 방향에 포함되지만 초기 MVP 범위에서는 제외한다.

---

# 9. 대표 사용자 시나리오

## Scenario 1. 친구 블로그 추가

사용자는 친구가 운영하는 블로그를 지속적으로 읽고 싶다.

친구는 Blog.zip에 가입되어 있지 않다.

사용자는 Blog.zip에서 친구의 블로그 URL을 입력한다.

Blog.zip은 해당 URL에서 블로그 정보와 Feed를 탐색한다.

탐색에 성공하면 사용자에게 다음과 같이 묻는다.

> 누구의 블로그인가요?

사용자는 자신이 알아보기 위한 친구 이름을 입력한다.

해당 블로그는 친구 목록과 Feed에 추가된다.

친구가 Blog.zip에 가입하지 않아도 이후 해당 블로그의 새로운 글을 받아볼 수 있다.

---

## Scenario 2. 여러 플랫폼의 친구 글 확인

사용자는 여러 친구의 블로그를 구독하고 있다.

각 블로그는 서로 다른 플랫폼에서 운영된다.

Blog.zip은 새로운 게시물을 수집해 하나의 피드로 구성한다.

사용자는 각 플랫폼을 직접 방문하지 않고 Blog.zip에서 새로운 글을 발견한다.

글을 선택하면 원문을 확인할 수 있다.

---

## Scenario 3. 내 블로그 연결

사용자는 자신의 블로그도 운영하고 있다.

사용자는 Blog.zip의 내 블로그 연결 기능에 블로그 URL을 입력한다.

Blog.zip은 소유권 인증 절차를 제공한다.

인증에 성공하면 해당 Blog와 User 사이에 Ownership 관계가 생성된다.

---

## Scenario 4. 기존 구독 Blog의 소유자 가입

특정 Blog는 이미 여러 사용자가 구독하고 있다.

이후 실제 Blog 운영자가 Blog.zip에 가입하고 해당 블로그의 소유권을 인증한다.

기존 Subscription 관계는 유지된다.

Blog에 실제 운영자의 User 정보가 연결될 수 있지만 기존 구독자가 개인적으로 지정한 이름은 임의로 변경하지 않는다.

---

# 10. 핵심 사용자 흐름

## 친구 블로그 추가

```text
Home
↓
친구 블로그 추가
↓
블로그 URL 입력
↓
Blog / Feed 탐색
↓
블로그 정보 확인
↓
"누구의 블로그인가요?"
↓
이름 입력
↓
Subscription 생성
↓
친구 Feed에 추가
```

```text
외부 Blog에 새로운 글 작성
↓
Blog.zip이 새로운 Post 탐지
↓
Post 저장
↓
구독자의 Feed에 노출
↓
사용자가 Post 선택
↓
원문 이동
```

---

## 내 블로그 연결

```text
Profile
↓
내 블로그 연결
↓
블로그 URL 입력
↓
Blog 탐색
↓
소유권 인증
↓
Ownership 생성
↓
Profile과 Blog 연결
```

# 11. MVP 범위

## Must Have

### 계정

- 회원가입
- 로그인
- 로그아웃

### 블로그 구독

- 블로그 URL 입력
- 지원 가능한 Blog인지 확인
- Feed 자동 탐색
- 블로그 기본 정보 조회
- 누구의 블로그인지 이름 지정
- Subscription 생성
- Subscription 삭제

### Feed

- 구독한 Blog의 Post 수집
- 최신 Post 목록 제공
- 친구 이름 표시
- 게시물 제목 표시
- 게시 날짜 표시
- 블로그 또는 플랫폼 정보 표시
- 원문 이동

### 내 블로그

- 본인 Blog URL 등록
- Blog 소유권 인증
- Ownership 생성
- 연결된 내 Blog 확인
- Ownership 해제

### 관리

- 구독한 친구 목록 조회
- 사용자가 지정한 친구 이름 수정
- 구독 해제

- 동일 Blog 중복 구독 방지

- 마지막 정상 수집 시간 표시

# 13. 제품 수준 Business Rules

## BR-001

Subscription은 Ownership을 의미하지 않는다.

## BR-002

사용자는 공개적으로 접근 가능한 Blog를 소유권 인증 없이 구독할 수 있다.

## BR-003

Blog를 자신의 것으로 계정에 연결하려면 Ownership 인증이 필요하다.

## BR-004

Subscription 생성 시 사용자가 입력한 친구 이름은 해당 사용자에게만 적용된다.

## BR-005

동일 Blog를 다른 사용자가 서로 다른 이름으로 저장할 수 있다.

## BR-006

Blog 운영자가 Blog.zip에 가입하지 않아도 해당 Blog를 구독할 수 있다.

## BR-007

Blog 운영자가 이후 가입하여 Ownership을 인증하더라도 기존 Subscription은 유지된다.

## BR-008

Ownership 인증 전에는 해당 Blog의 공식 운영자임을 서비스에서 보장해서는 안 된다.

## BR-009

Feed에서 제공되는 콘텐츠는 반드시 원본 Blog 및 Post 출처를 확인할 수 있어야 한다.

## BR-010

Blog.zip에서 사용자가 지정한 친구 이름을 근거로 실제 Blog 소유자를 자동 확정해서는 안 된다.

---

# 14. 지원 플랫폼 방향

Blog.zip은 특정 블로그 플랫폼에 종속되지 않는 것을 목표로 한다.

초기 지원 우선순위는 실제 사용성 및 Feed 지원 여부를 기준으로 결정한다.

우선 검토 대상:

- Naver Blog
- Velog
- Tistory
- RSS 지원 개인 블로그
- Atom 지원 개인 블로그

새로운 플랫폼 지원 여부 및 탐지 방법은 각각의 Feature Spec과 Technical Decision에서 관리한다.

PRD에서는 특정 크롤링 방식 또는 Feed Parser 구현 방법을 정의하지 않는다.

---

# 15. 성공 지표

초기 제품 검증 단계에서는 사용자 수 자체보다 **친구 Blog를 실제로 등록하고 다시 방문하는지**를 중심으로 본다.

## Activation

- 가입 사용자 중 Blog 1개 이상 구독한 사용자 비율
- 가입 후 첫 Subscription 생성까지 걸리는 시간
- 사용자당 평균 Subscription 수

## Engagement

- Weekly Active User
- 사용자당 주간 Feed 조회 횟수
- Feed에서 원문으로 이동하는 비율
- 사용자당 주간 조회 Post 수

## Retention

- 7일 재방문율
- 30일 재방문율
- Subscription 유지율

## Social Expansion

- 내 Blog 연결 비율
- 친구 초대 기능 도입 이후 초대 비율
- 기존 구독 Blog 운영자의 가입 전환율

# 18. 문서 관계

본 문서는 Blog.zip의 **제품 수준 요구사항에 대한 Source of Truth**이다.

기능별 상세 동작은 `docs/specs/`를 기준으로 한다.

기술적 구현 방식과 장기적으로 유지되는 설계 결정은 `docs/decisions/`에서 관리한다.

개발 시 다음 우선순위를 따른다.

```text
PRD
↓
Feature Spec
↓
Technical Decision
↓
GitHub Issue
↓
Implementation
```

PRD는 다음 내용을 정의한다.

```text
무엇을 만드는가
왜 만드는가
누구를 위한 제품인가
제품의 범위는 어디까지인가
제품 수준에서 지켜야 할 원칙은 무엇인가
```

Feature Spec은 다음 내용을 정의한다.

```text
각 기능이 어떻게 동작해야 하는가
어떤 비즈니스 규칙을 따라야 하는가
어떤 예외 상황을 처리해야 하는가
어떤 조건을 만족하면 완료된 것인가
```

Technical Decision은 다음 내용을 정의한다.

```text
기술적으로 어떤 방식을 선택했는가
왜 해당 방식을 선택했는가
어떤 대안을 검토했는가
어떤 Trade-off가 존재하는가
```

코드와 문서가 충돌하는 경우 기존 구현을 기준으로 PRD 또는 Spec을 자동으로 수정하지 않는다.

먼저 어떤 동작이 올바른 요구사항인지 확인하고 잘못된 쪽을 수정한다.

# 19. 핵심 제품 정의

Blog.zip의 핵심은 다음 한 문장으로 정의한다.

> **친구가 어디에서 블로그를 쓰든, 한곳에서 계속 만날 수 있도록 한다.**

Blog.zip은 블로그 플랫폼을 통합하려는 서비스가 아니라,

**플랫폼에 의해 분리된 사람과 글의 관계를 다시 연결하는 서비스**를 지향한다.
